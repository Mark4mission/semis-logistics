검토마다 시험 5종을 돌리고, 수정을 하나씩 되돌린 사본(돌연변이)으로 시험이 잡는지 확인했다. 마지막 검토에서 남은 돌연변이는 결과가 같은 코드(동등)뿐이다.

| # | 내용 · 고친 방법 |
|---|---|
| C1 | R0 뒤 K → H 만인 연결에서 [삭제 확정] 거절 → 다음 실행이 다시 삭제 대기로 → 되풀이 → 그 경우 건너뜀(`dir`, 세지 않음) |

| C5 | R16 이 건수만 보고 비율은 안 봄(작은 연결의 폴더 통째 삭제가 통과) → 승인 건수를 넘는 부분에 건수 · 비율 · 최소 건수를 모두 적용(세 곳 같은 규칙) |

| C11 | (2회차 검토 · 원래 있던 결함) K → H 만인 연결에서 H 새 판 뒤 [복원]이 실패(`ksync_get` 이 옛 주소만 허용) → 오류 'state'(엉뚱하게 '연결 멈춤' 안내) → 다시는 복원 못 함 → `ksync_get` 이 같은 연결 · 같은 판 묶음의 복원 줄도 받음(다른 판 묶음은 그대로 거절) |
| C12 | (2회차 검토) R1 에서 H → K 만인 연결은 확정 뒤 K 에서 고친 파일도 휴지통으로(30일 뒤 지워짐) → 옮기지 않고 K 에 남긴 채 기준선 줄만 지움(그 연결은 추적하지 않는 K 파일을 올리지 않으므로 되풀이 없음) |
| C13 | (3회차 검토) K 에서 지운 뒤 H 사용자가 그 문서를 다른 판 묶음으로 옮기면 [삭제 확정]이 'H 에 새 판'으로 잘못 거절 → 되풀이 → 확정은 그 파일 주소를 현재 판으로 가진 판 묶음을 따라가고, 그때는 그 주소의 첨부만 지움(옮겨 간 판 묶음의 다른 판은 그 파일의 이력이 아니므로 이름 · 첨부 하나 규칙을 쓰지 않음). 고치며 넣은 안전장치(늘 적용): 같은 연결의 다른 기준선 줄이 추적하는 첨부는 지우지 않음(원래 있던 결함도 함께 고침 — 같은 문서에 `r.pdf` 두 개면 하나를 확정해도 둘 다 지워짐) · SSI 아닌 연결은 SSI 문서 · docs-ssi 파일을 지우지 않음 · 이번에 비게 된 문서만 지움(처음부터 첨부 없던 판은 남김) |
| C14 | (3회차 검토 · 마지막 수정자가 찾음) 첨부가 많은 H 새 문서를 받을 때 서버가 두 번째 첨부부터 '덮어쓰기'로 셈(첫 첨부의 기준선 줄이 그 실행에서 생김) → 작은 연결에서 거짓 대량 변경 보류. E2E 는 한도를 올려 피해 가고 있었음 → 서버는 실행 시작 때 찍은 기준선 판 묶음 목록(`ksync_run_sers`, 계획과 같은 거름)에 있는 것만 셈. 다시 보낸 표시(R4) 뒤 받는 `hello full` 이 같은 거래 안에서 목록을 다시 찍음(그 에이전트의 열린 실행 · 아직 센 것이 없을 때만). 올리기 시작의 'new → 새 판' 셈도 계획과 같게(현재 판에 이름 · 저장 주소가 있는 첨부가 있을 때만). E2E 우회를 지우고 19-6-1 추가: 파일 3개 연결 · 첨부 25개 새 문서 → 보류 없음 |
| C15 | (3회차 검토) SQL 주석에 '예전처럼' 같은 변경 이력 표현 → 동작을 바로 쓰도록 고침(주석은 이유만) |
